# YOLO Project Workflow

This repository follows the standard `yolo_manager` project layout for YOLO
dataset building, training, evaluation, experiment tracking, and optional online
synthetic training data.

## Project Layout

```text
Configs/
    Dataset_configs/
    Evaluation_configs/
    HPC_configs/
    HPO_configs/
    Synthetic_data_configs/
    Training_configs/
        trainability_policies.yaml
Data/
    Natural_data/
    Synthetic_data/
Datasets/
    <dataset_family>/
        <dataset_name>/
Experiments/
```

Bare config names are resolved from their matching `Configs/<type>/` directory.
Config names may contain dots. For example, `yolo-train -t screw.v1` resolves to
`Configs/Training_configs/screw.v1.yaml`.

## CLI Commands

```bash
yolo-init -r <repo_dir> [-o]
yolo-dataset -d <dataset_config>
yolo-uuid -f <data_source>
yolo-train -t <training_config> [-o] [-s <synthetic_config>]
yolo-eval -e <eval_config>
yolo-train-hpc -t <training_config> -c <hpc_config> [-p <hpo_config>] [-o] [-s <synthetic_config>]
yolo-test-generation -s <synthetic_config> -n <test_name>
```

All config arguments accept either a bare config name with or without `.yaml`,
or a direct YAML path.

## Dataset Workflow

1. Place source data under `Data/Natural_data/<source>/` or `Data/<source>/`.
2. Use the following source structure:

```text
Data/Natural_data/<source>/
    images/
    labels/
```

3. Optionally rename image and label pairs with UUIDs:

```bash
yolo-uuid -f <source>
```

4. Create a dataset config in `Configs/Dataset_configs/`.
5. Build the dataset:

```bash
yolo-dataset -d example_dataset_config
```

The generated dataset is written to `Datasets/<dataset_family>/<dataset_name>/`
when `dataset.family` is set. Legacy dataset configs without `family` still
write to `Datasets/<dataset_name>_v<version>/`. Each dataset contains split
folders, `data.yaml`, and an autogenerated dataset card.

## Local Training

Create a training config in `Configs/Training_configs/` and start training:

```bash
yolo-train -t example_train_config
```

Training creates an experiment folder:

```text
Experiments/<experiment_group>/<experiment_name>/
    Run/
    configuration/
    Evaluation/
    README.md
```

Use `-o` only when an existing experiment should be overwritten. The CLI asks for
confirmation before overwriting.

Early stopping patience is configured with the training parameters:

```yaml
training_params:
  epochs: 300
  patience: 100  # 0 disables early stopping
```

`patience` counts epochs without validation-fitness improvement. If omitted,
the Ultralytics default remains active.

### Base Models and Fine-Tuning

Training configs can use normal Ultralytics model names:

```yaml
setup:
  yolo_base_model: yolo11s.yaml
```

They can also reference an existing checkpoint from this project layout:

```yaml
setup:
  yolo_base_model:
    experiment_group: Universal_screw_detection
    experiment_name: 3.3
    weights: best.pt
```

This resolves to:

```text
Experiments/Universal_screw_detection/3.3/Run/weights/best.pt
```

`weights` accepts `best`, `best.pt`, `last`, or `last.pt`.

Optional trainability policies can be set in `training_params`:

```yaml
training_params:
  trainability_policy: backbone_frozen
  trainability_prefixes: null
```

Available policies:

- `full`: normal training behavior
- `head_only`: train only the task head
- `neck_head`: train neck and head
- `head_and_last_stage`: train the task head and its direct input feature modules
- `backbone_frozen`: freeze the YAML backbone, train the rest
- `custom_prefixes`: train only parameters matching `trainability_prefixes`

The compact reference file
`Configs/Training_configs/trainability_policies.yaml` is included in generated
repositories.

### Experiment Series

Experiment series are configured directly in the training config. Values to
vary use YAML set syntax `{...}`:

```yaml
experiment_series:
  enable: true
  mode: grid
  seed_repeats: 2

training_params:
  learning_rate: {0.008, 0.001}
  trainability_policy: {head_only, head_and_last_stage}
  seed: 41252
```

`mode: grid` runs all combinations. `mode: sample` samples
`experiment_series.sample_runs` combinations from the same grid. Lists are not
accepted for varied values. The seed base is `training_params.seed`; generated
seeds are written into each run's archived config.

Before a series starts locally or is submitted via `yolo-train-hpc`, the CLI
prints the varied parameters, combination count, seed repeats, total run count,
and output folder, then asks for confirmation.

Series outputs are written below the experiment folder:

```text
Experiments/<experiment_group>/<experiment_name>/
    series_config.yaml
    manifest.json
    summary.csv
    summary.json
    summary.md
    plots/
        metrics_by_run.html
    runs/
        run_001/
            Run/
            configuration/
            Evaluation/
            README.md
```

Each run stores a concrete `configuration/train_config.yaml` with the selected
scalar values and generated seed.

### Fitness Target

By default, Ultralytics decides `best.pt` and early stopping with its standard
detection fitness, effectively `mAP50-95(B)`.

To use a custom weighted fitness, add:

```yaml
training_params:
  target:
    precision: 0.0
    recall: 0.2
    map50: 0.3
    map50_95: 0.5
```

The weights correspond to `[P, R, mAP50, mAP50-95]`. `P` and `R` are mean
precision and mean recall on the validation set. If `target` is missing or
`null`, the Ultralytics default remains active.

### Optional Test Split

`data.yaml` must contain usable `train` and `val` splits. The `test` split can
be disabled intentionally:

```yaml
test: null
```

Disabled test values are `null`, `None`, `~`, an empty string, or an empty list.
Training and validation still run; only the final post-training test evaluation
is skipped.

## Online Synthetic Training

Synthetic training is optional. Without `--synthetic-config`, training uses the
normal Ultralytics dataset path.

To enable synthetic samples during training:

```bash
yolo-train -t example_train_config -s example_synthetic_data_config
```

The synthetic config lives in `Configs/Synthetic_data_configs/` and must define:

```yaml
setup:
  data: Data_name
  num_synthetic_train_samples: 100
```

Synthetic assets are resolved below `Data/Synthetic_data/<Data_name>/`:

```text
Data/Synthetic_data/<Data_name>/
    objects/
        images/
        labels.csv        # optional class mapping
    background/
        images/
        zones/
```

When synthetic training is enabled:

- the training split uses a hybrid real/synthetic dataset
- validation and evaluation remain real-data only
- synthetic samples are generated online while training loads samples
- Mosaic and MixUp can combine real and synthetic samples
- resource paths and one generated sample are validated before training
- 20 annotated preview images are saved under `synthetic_samples/`
- the used synthetic config is archived in `configuration/synthetic_config.yaml`
- synthetic metadata is added to the experiment card

Selected synthetic parameters can be optimized during HPO when the HPO job is
submitted with both `-p <hpo_config>` and `-s <synthetic_config>`.

## Synthetic Test Generation

Generate a fixed synthetic image and label set before training:

```bash
yolo-test-generation -s example_synthetic_data_config -n smoke_test
```

The command uses the same synthetic config and asset layout as online
synthetic training.

- `-s` specifies the synthetic config from `Configs/Synthetic_data_configs/` or
  a direct YAML path.
- `-n` specifies the output folder below
  `Data/Synthetic_data/<Data_name>/test_images/`.
- The number of generated images is read from
  `setup.num_synthetic_train_samples`.
- Terminal output reports total generation time, average time per image, CPU
  time, and average CPU time per image.

Output is written below:

```text
Data/Synthetic_data/<Data_name>/test_images/<test_name>/
    images/
    labels/
```

These generated folders can be inspected manually or referenced from dataset
configs like any other source when you want to build a fixed dataset.

## Evaluation

Create an evaluation config in `Configs/Evaluation_configs/`:

```yaml
setup:
  evaluation_name: example_eval
  experiment_group: Experiment_Group
  experiment_name: 1.0
  split: test

dataset:
  family: Dataset_Family
  name: Dataset_Name

model:
  weights: best.pt

validation_params:
  imgsz: 640
  batch: 16
  conf: 0.25
  iou: 0.7
```

Run evaluation:

```bash
yolo-eval -e example_eval_config
```

Outputs are written to:

```text
Experiments/<experiment_group>/<experiment_name>/<evaluation_name>/
    eval_config.yaml
    metrics.json
    test_metrics/
    test_predictions/
```

## HPC And HPO

Submit a normal training job:

```bash
yolo-train-hpc -t example_train_config -c example_hpc_config
```

Submit HPO followed by final training:

```bash
yolo-train-hpc -t example_train_config -c example_hpc_config -p example_hpo_config
```

Synthetic training can also be enabled on HPC:

```bash
yolo-train-hpc -t example_train_config -c example_hpc_config -s example_synthetic_data_config
```

Submit HPO with online synthetic data:

```bash
yolo-train-hpc -t example_train_config -c example_hpc_config -p example_hpo_config -s example_synthetic_data_config
```

The HPC workflow uses `submitit` and was prepared for RWTH CLAIX-style SLURM
clusters. Other clusters may require changes to the HPC config.

HPO uses `optuna.target` to define the fitness optimized by Optuna. The same
fitness is passed into training, so HPO trials, `best.pt`, and early stopping
use the same target:

```yaml
optuna:
  direction: maximize
  target:
    precision: 0.0
    recall: 0.2
    map50: 0.3
    map50_95: 0.5
```

`optuna.metric_to_optimize` is no longer used.

Example HPO search-space entries:

```yaml
search_space:
  training_params.learning_rate:
    type: float
    low: 1e-5
    high: 1e-2
    log: true

  training_params.trainability_policy:
    type: categorical
    choices: [full, backbone_frozen, neck_head, head_and_last_stage, head_only]
```

Synthetic HPO entries are supported when a synthetic config is provided:

```yaml
search_space:
  num_synthetic_train_samples:
    type: int
    low: 0
    high: 200
    step: 50

  placement.objects_per_image.min:
    type: int
    low: 0
    high: 2

  placement.objects_per_image.max:
    type: int
    low: 4
    high: 8
```

The short key `num_synthetic_train_samples` maps to
`setup.num_synthetic_train_samples` in the synthetic config. Explicit synthetic
prefixes such as `synthetic.placement.objects_per_image.max` are also accepted.

## Documentation Expectations

Autogenerated dataset and experiment cards are starting points. Review and enrich
them after each dataset build or training run with:

- acquisition details and labeling rules
- qualitative evaluation findings
- known limitations
- intended use and deployment notes
- experiment history and release decisions
